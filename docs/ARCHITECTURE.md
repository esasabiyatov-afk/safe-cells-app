# Архитектура приложения

## 1. Назначение и границы

Приложение работает без интернета. На рабочем столе сотрудника находится веб-ярлык «Сейфовые ячейки». Сотрудник нажимает только его: ярлык без консольного окна запускает локальный `safe-cells.exe` из папки установки, поднимает Flask-сервер только на `127.0.0.1` и открывает Chrome или другой браузер по умолчанию. Общими являются только рабочая и архивная SQLite-базы и каталог шаблонов на сетевом диске банка.

Статический `.html` сам по себе не может безопасно обращаться к SQLite и выполнять транзакции. Поэтому `.exe` сохраняется как невидимый технический компонент, но сотрудник не взаимодействует с ним напрямую.

Центральный сервер, CDN, облачные сервисы, телеметрия, Node.js и frontend-фреймворки не используются. Разработка и автоматические тесты работают только с временными локальными каталогами и вымышленными данными.

## 2. Состав приложения

```text
browser (HTML/CSS/JS)
        |
        | HTTP только 127.0.0.1 + токен экземпляра
        v
Flask routes
        |
        +-- services: расчёты и бизнес-правила
        +-- db: короткие SQLite-соединения и транзакции
        +-- documents: проверка и заполнение DOCX
        +-- backups: согласованные резервные комплекты
        +-- runtime: порт, локальный выбор сотрудника, запуск браузера, завершение
        |
        v
общая сетевая папка
  vault_cells.sqlite3
  vault_archive.sqlite3
  templates/
  backups/
```

HTTP-маршруты не содержат SQL и финансовых формул. Сервисы не зависят от HTML. Доступ к БД, документы, бэкапы и управление процессом разделяются на отдельные модули.

## 3. Запуск и доступность данных

Обычный запуск никогда не создаёт производственную базу. Он:

1. Читает локальный конфигурационный файл с путём к общей папке.
2. Проверяет, что путь, оба файла БД и каталог шаблонов доступны.
3. Открывает обе базы только для чтения и выполняет `PRAGMA quick_check`.
4. При успехе запускает интерфейс; при ошибке показывает безопасный экран без персональных данных.

Первое создание схемы выполняется отдельной административной командой с явным подтверждением и только в указанной пустой общей папке. Недоступный UNC-путь, отсутствующий файл или повреждённая база не заменяются локальной копией.

## 4. Чтение

Каждый просмотр открывает новое URI-соединение вида `file:...?mode=ro`, включает `foreign_keys`, задаёт `busy_timeout`, выполняет только `SELECT` и закрывается в `finally`.

Главный экран перечитывается при открытии, после успешного изменения, по кнопке «Обновить» и примерно раз в 15 секунд. Фильтры по статусу, высоте и номеру применяются к уже загруженному безопасному набору данных в браузере.

ФИО и номер счёта не включаются в общий список ячеек. Поиск по этим полям выполняется отдельным коротким read-only запросом и возвращает только номера совпавших ячеек. Это безопасное уточнение исключает массовую передачу персональных данных в браузер до команды «Показать данные».

## 5. Запись и конкурентная работа

Каждое подтверждённое изменение получает уникальный `operation_id`. Алгоритм записи:

1. Открыть короткое read/write-соединение к рабочей базе.
2. Установить `foreign_keys=ON`, `busy_timeout=15000`, `journal_mode=DELETE`, `synchronous=FULL`, `locking_mode=NORMAL`.
3. При необходимости подключить архив через `ATTACH DATABASE` и применить безопасные настройки к нему.
4. Выполнить `BEGIN IMMEDIATE`.
5. Повторно прочитать данные внутри транзакции и проверить инварианты.
6. Проверить, не выполнялся ли этот `operation_id` ранее.
7. Изменить рабочую и/или архивную базу параметризованными запросами.
8. Выполнить `COMMIT`; при любой ошибке — `ROLLBACK`.
9. Закрыть соединение в `finally`.
10. Перечитать сохранённое состояние. При неопределённом сетевом результате не повторять запись автоматически, а проверить `operation_id`.
11. Создать проверенный комплект резервных копий.

Так как `contracts` содержит только активные договоры, `UNIQUE(cell_number)` на уровне рабочей БД не позволяет занять одну ячейку дважды. Состояние «свободна/занята» не хранится отдельным флагом: оно выводится из наличия активного договора и поэтому не может разойтись с договором.

Если другая запись не освободила БД за 15 секунд, пользователь получает понятное сообщение, транзакция откатывается, автоматического повтора нет. WAL запрещён.

## 6. Атомарные операции двух баз

Создание договора, продление, закрытие и административные изменения одновременно пишут бизнес-данные в рабочую базу и аудит в архивную. Архив подключается до `BEGIN IMMEDIATE`; все изменения завершаются одним `COMMIT`.

При закрытии порядок внутри одной транзакции такой:

1. Повторно проверить активный договор и дату закрытия.
2. Вставить полную запись в `archive.contracts_archive`.
3. Вставить действие в `archive.log`.
4. Удалить активный договор из `main.contracts`.
5. Выполнить общий `COMMIT`.

Внешние ключи SQLite не работают между подключёнными файлами. Поэтому договор имеет неизменяемый UUID `contract_id`, который сохраняется во всех архивных записях; согласованность дополнительно проверяет сервис и интеграционные тесты.

## 7. Даты, статусы и деньги

Все календарные даты хранятся как ISO `YYYY-MM-DD`, время аудита — ISO с часовым поясом компьютера. Расчёты получают дату явно; тесты не используют текущую дату напрямую.

- Аренда: `days = end_date - start_date + 1`.
- Конец по числу дней: `end_date = start_date + days - 1`.
- Продление: `max(0, renewal_date - old_end_date - 1 day)`.
- Закрытие: `max(0, close_date - end_date)`.
- Штрафная ставка определяется административным режимом: тариф диапазона 1–30 дней либо отдельная ручная ставка для высоты ячейки. Фактическая ставка сохраняется снимком в операции.

Frontend показывает предварительный расчёт, но backend заново вычисляет и проверяет даты, дни, тариф и итог перед сохранением. Клиентскому браузеру нельзя доверять финансовые значения.

Статус занятой ячейки при пороге `N` дней:

- `overdue`, если `end_date < as_of_date`;
- `expiring`, если `0 <= end_date - as_of_date <= N`;
- `normal`, если остаток больше `N`.

Единственная валюта приложения — сом (`KGS`), поэтому сотрудник не выбирает валюту в калькуляторе. Дробные суммы не допускаются: все тарифы, залог, стоимость и штраф хранятся целыми числами, а `float` не используется. Начальный залог равен 1500 сом и редактируется администратором в том же разделе настроек, что и тарифы.

## 8. Персональные данные и журнал

Общий список ячеек не содержит персональных полей. Полная карточка получает их отдельным запросом только после «Показать данные». HTML использует штатное экранирование шаблонов; JavaScript вставляет пользовательские строки через безопасные текстовые свойства, а не через `innerHTML`.

Есть два разных журнала:

- технический лог — только код ошибки, тип операции и обезличенный идентификатор; без ФИО, ID-карты и счёта;
- `archive.log` — банковский аудит изменений, доступный только через предусмотренный интерфейс и хранящий разрешённые старые/новые значения как защищаемые бизнес-данные.

Пароль администратора хранится только как стойкий хеш с солью. Пароля по умолчанию нет; первоначальная настройка выполняется явно. Все изменяющие HTTP-запросы требуют токен текущего локального экземпляра и защиту от повторной отправки.

## 9. Документы

DOCX-шаблоны лежат в общем каталоге `templates` и выбираются по метаданным из рабочей БД. Абсолютные пути в БД не сохраняются. Известные плейсхолдеры и обязательные данные проверяются до публикации каждого комплекта.

Чтобы не держать сетевую SQLite-блокировку во время обработки DOCX, порядок следующий:

1. Выполнить и подтвердить короткую транзакцию БД.
2. Заново прочитать сохранённые данные через короткие `mode=ro`-соединения.
3. Полностью подготовить и проверить комплект во временной папке внутри «Загрузок».
4. Опубликовать готовые файлы через атомарное переименование.

Если подготовка или финальное перемещение не удалось после `COMMIT`, данные не откатываются и бизнес-операция автоматически не повторяется: пользователю отдельно сообщается, что действие сохранено, а документы не сформированы. Внутренний реестр сформированных файлов не ведётся.

## 10. Резервные копии и восстановление

После подтверждённой записи создаётся комплект из двух баз через SQLite Backup API. Обычная write-транзакция и снятие пары снимков используют одну межпроцессную блокировку в общей папке, поэтому другой экземпляр не может записать данные между копированием рабочей и архивной баз. SQLite по-прежнему применяет `BEGIN IMMEDIATE`, DELETE journal, FULL synchronous и NORMAL locking как основную защиту данных.

Обе копии сначала создаются внутри одного скрытого временного каталога. Для каждой выполняется `quick_check`, рассчитываются размер и SHA-256, затем создаётся и повторно проверяется `manifest.json`. Единственная точка публикации — атомарное переименование всего каталога; поэтому две копии и манифест появляются как один завершённый комплект.

Хранятся последние 30 полностью валидных комплектов. Незавершённые временные файлы не считаются комплектом. Обычное копирование активных файлов и автоматическая замена рабочих баз запрещены.

Каждый локальный процесс удерживает обезличенный маркер-блокировку в `.safe_cells_instances`. Обнаруженное повреждение записывает технический `write-block.json`, и каждое последующее открытие write-соединения отклоняется до контролируемого восстановления. Маркеры не содержат ФИО, путей, паролей или секретов.

Восстановление — отдельный административный режим. Оно не запускается автоматически и разрешено только при существующей блокировке повреждения. Сервис повторно проверяет манифест, SHA-256 и `quick_check`, получает общую maintenance-блокировку, проверяет отсутствие других активных экземпляров, сохраняет обе исходные базы в `damaged-originals` и публикует обе восстановленные базы. После успеха в архив записывается только технический идентификатор комплекта/карантина и создаётся новый контрольный комплект. Реальная процедура обязательно проверяется на копиях и на тестовой сетевой папке.

## 11. Ярлык и завершение локального экземпляра

Установщик создаёт на рабочем столе ярлык с названием и значком веб-приложения. Его цель — скрытый локальный launcher, а не файл базы и не удалённый сайт. Каждый процесс слушает только свой порт и использует случайный токен экземпляра. Сигнал закрытия вкладки относится только к этому процессу. Чтобы обновление страницы не завершало приложение ошибочно, сервер применяет короткий период ожидания и отменяет завершение, если вкладка подключилась снова. Дополнительно будет явная кнопка «Выйти». Ограничения браузеров и финальное поведение проверяются в собранном `.exe`.

## 12. Остаточные риски утверждённой архитектуры

- SQLite на сетевом диске зависит от корректной реализации файловых блокировок SMB и стабильности сети.
- Атомарность SQLite не делает формирование DOCX частью транзакции БД.
- Бэкап после каждой записи увеличивает время блокировки по мере роста архива.
- Выбор сотрудника хранится только в памяти локального процесса и не является строгой аутентификацией; модель рассчитана на доверенный отдел и защищённую банковскую сеть.
- Проверки на локальном диске не заменяют приёмку на фактическом сетевом томе с 1–3 тестовыми экземплярами.

Эти риски снижаются тестами, короткими соединениями, `BEGIN IMMEDIATE`, уникальными ограничениями, идемпотентностью операций, проверенными бэкапами и обязательной сетевой приёмкой, но не могут быть устранены полностью без изменения утверждённой архитектуры.
