# ТЗ: приложение для управления банковскими сейфовыми ячейками

## 1. Контекст

Локальное веб-приложение для банка. Работает без интернета, в локальной сети/на компьютере сотрудника. Не интегрируется напрямую с АБС — сотрудник получает данные клиента и номер счёта в АБС отдельно, затем вручную вводит их в приложение.

Пользователь (заказчик) не программист, направляет требования, весь код пишет ИИ. Объяснения — простым языком, без лишнего жаргона.

Приложение должно:

- показывать состояние всех сейфовых ячеек;
- рассчитывать стоимость аренды;
- оформлять занятие ячейки;
- продлевать аренду;
- закрывать договор;
- рассчитывать просрочку и штраф;
- формировать договоры, акты, дополнительные соглашения и распоряжения из шаблонов;
- сохранять актуальные данные о состоянии ячеек в базе данных.

Сгенерированные документы не хранятся внутри приложения и не учитываются в отдельном реестре — после заполнения шаблона файл выгружается в папку «Загрузки» и используется в бумажном виде.

## 2. Технический стек и архитектура запуска

- Backend: Python (Flask), упаковывается в один .exe (PyInstaller) — сотрудник ничего не устанавливает
- Frontend: обычные HTML/CSS/JS, без сборщиков и фреймворков
- База данных: SQLite, две отдельные базы (см. раздел 12) — лежат на сетевом диске рядом с exe
- Запуск: клик по exe → сервер стартует в фоне без видимого окна консоли → автоматически открывается вкладка браузера
- Несколько сессий одновременно: приложение при старте само ищет свободный порт (5000, 5001, 5002...), позволяя 2-4 сотрудникам работать параллельно
- Закрытие: закрытие вкладки браузера автоматически посылает сигнал серверу на завершение процесса
- Надёжность записи данных (приоритет):
  - atomic write (запись во временный файл, затем замена основного)
  - короткие подключения к БД — открываются только на момент записи
  - блокировка при одновременной записи двух сессий
  - автоматический бэкап после каждого сохранения, хранить последние 30 версий
  - проверка целостности базы при старте, восстановление из последнего валидного бэкапа при повреждении

## 3. Идентификация сотрудника

Отдельного экрана логина/пароля для обычной работы нет. Сотрудник, работающий в приложении, определяется автоматически по имени учётной записи Windows на компьютере (логин компьютера). Это имя отображается в углу интерфейса на протяжении всей работы и используется как значение «Сотрудник» в журнале действий и в документах.

Для административных функций (редактирование тарифов, шаблонов документов, добавление/редактирование ячеек — см. раздел 13) — отдельный пароль на вход в раздел настроек, не связанный с системой ролей по логину.

## 4. Состояния сейфовой ячейки

Два основных состояния:

1. Свободна.
2. Занята.

Для занятой ячейки автоматически определяется одно из трёх подсостояний:

- нормально;
- срок аренды истекает;
- просрочена.

Подсостояние вычисляется интерфейсом на основании текущей даты и даты окончания аренды, вручную не меняется. Порог для статуса «Истекает» (количество дней) задаётся в настройках (таблица `config`, раздел 11).

Цвета: свободная — зелёный; занята, срок нормальный — синий; истекает — жёлтый/оранжевый; просрочена — красный.

## 5. Модель размеров ячеек

Размер ячейки — не категория (не «малая/средняя/большая»), а точный физический размер, закреплённый за конкретным номером навсегда.

Ширина и глубина одинаковы для всех текущих 126 ячеек (220 мм и 330 мм). Переменная величина — высота. Не дублировать постоянные значения в каждой строке — вынести в отдельную таблицу значений по умолчанию.

```sql
CREATE TABLE vault_defaults (
    width_mm INTEGER,
    depth_mm INTEGER
);
-- одна строка: width_mm = 220, depth_mm = 330

CREATE TABLE cells (
    number TEXT PRIMARY KEY,
    height_mm INTEGER NOT NULL,
    width_mm INTEGER,   -- NULL = взять из vault_defaults
    depth_mm INTEGER    -- NULL = взять из vault_defaults
);
```

Реальные номера ячеек и их высота — в приложенном файле `cell_heights.csv` (126 строк: number, height_mm). Загрузить как seed-данные при первом запуске.

Уникальных значений высоты — 6: 50, 75, 100, 125, 175, 300 мм.

## 6. Тарифы

Тарифы не должны быть жёстко прописаны в коде — редактируются через раздел настроек (доступ администратора, раздел 3).

```sql
CREATE TABLE tariffs (
    height_mm INTEGER NOT NULL,
    period_from_days INTEGER NOT NULL,
    period_to_days INTEGER,      -- NULL = без верхней границы (181+)
    price_per_day REAL NOT NULL,
    PRIMARY KEY (height_mm, period_from_days)
);
```

Актуальные значения (цена за один день аренды, зависит от высоты ячейки и от диапазона длительности всего срока аренды):

| Высота, мм | До 30 дней | 31–90 дней | 91–180 дней | 181+ дней |
|---|---|---|---|---|
| 50  | 15 | 10 | 8  | 7  |
| 75  | 17 | 13 | 11 | 8  |
| 100 | 17 | 13 | 11 | 8  |
| 125 | 20 | 15 | 13 | 10 |
| 175 | 25 | 20 | 15 | 13 |
| 300 | 30 | 25 | 20 | 17 |

Тариф выбирается по фактической длительности аренды целиком (не разбивается по дням внутри одного периода): аренда на 45 дней целиком идёт по ставке «31-90 дней».

Администратор выбирает единый режим штрафного тарифа: использовать строку «До 30 дней» для соответствующей высоты либо отдельную ручную ставку по каждой высоте. Выбранная ставка не зависит от ставки уже открытого основного договора.

## 7. Расчёт дней и стоимости — разделение GUI и backend

Чтобы не перегружать базу лишними промежуточными данными, расчёт разделён на два уровня:

**GUI (frontend, JavaScript):**
- Считает количество дней аренды по датам, сразу при вводе, без отдельной кнопки «Пересчитать»
- Дата начала и дата окончания аренды **обе включаются** в счёт дней: `количество_дней = (дата_окончания − дата_начала) + 1`
- При вводе количества дней вместо даты окончания — GUI сам вычисляет дату окончания: `дата_окончания = дата_начала + (количество_дней − 1)`
- Отображает пользователю количество дней сразу по мере ввода

**Backend («калькулятор»):**
- Получает от GUI готовое количество дней и номер ячейки (соответственно её высоту)
- Находит подходящую строку тарифа по высоте ячейки и по диапазону, в который попадает количество дней
- Считает стоимость: `стоимость = количество_дней × цена_за_день(высота, диапазон)`
- Не хранит и не пересчитывает сам количество дней — просто использует то, что уже посчитал и передал GUI

Пример: дата начала 01.07.2026, дата окончания 01.07.2026 → 1 день. Дата начала 01.07.2026, дата окончания 30.07.2026 → 30 дней.

Эта формула (включительно, +1) используется для основного срока аренды и для срока продления. Для расчёта штрафных дней используется другая, отдельная формула (раздел 9) — не путать.

## 8. Сценарий работы со свободной ячейкой

При нажатии на свободную ячейку открывается калькулятор аренды.

Принимает: дату начала + дату окончания, либо дату начала + количество дней аренды (см. раздел 7 про то, кто что считает).

Показывает: номер ячейки, высоту, дату начала, дату окончания, количество дней, применённый тариф, итоговую стоимость аренды (отдельной строкой), размер залога (отдельной строкой, из `config.deposit_amount`), общую сумму к оплате (стоимость + залог).

На этом этапе ячейка ещё не считается занятой, расчёт хранится временно, до подтверждения. Действия: «Назад», «Занять ячейку».

## 9. Оформление аренды

После согласия клиента сотрудник оформляет клиента и счёт в АБС, возвращается в приложение, выбирает рассчитанную ячейку, нажимает «Занять».

Сотрудник вводит: ФИО клиента, серию и номер ID-карты, орган выдачи, дату окончания ID-карты, номер счёта из АБС, остальные поля шаблонов.

После подтверждения:

1. Проверить обязательные поля.
2. Сохранить данные аренды в рабочей базе (таблица `contracts`).
3. Изменить состояние ячейки на «Занята».
4. Сформировать договор и необходимые акты из шаблонов, подставив данные.
5. Сохранить готовые документы в папку «Загрузки».
6. Показать сообщение об успешном оформлении.

Имя файла: тип документа + номер ячейки + ФИО клиента + дата.
Пример: `Договор_Ячейка-125_ИвановИИ_2026-06-27.docx`

## 10. Шаблоны документов

Поддерживаемые поля (примеры): `{{CLIENT_FULL_NAME}}`, `{{ID_CARD_NUMBER}}`, `{{ID_CARD_ISSUER}}`, `{{ID_CARD_EXPIRY_DATE}}`, `{{ACCOUNT_NUMBER}}`, `{{SAFE_NUMBER}}`, `{{SAFE_HEIGHT}}`, `{{START_DATE}}`, `{{END_DATE}}`, `{{RENT_DAYS}}`, `{{RENT_PRICE}}`, `{{CREATION_DATE}}`.

Типы шаблонов: договор аренды, акт передачи/открытия, дополнительное соглашение о продлении, распоряжение о закрытии, другие (добавляются администратором).

Перед формированием документа — проверка наличия всех полей шаблона, понятное сообщение при отсутствии.

## 11. Расчёт просрочки и продление

### Продление
Функция «Продлить» для занятой ячейки. Калькулятор продления принимает дату начала нового периода + новую дату окончания, либо количество дней продления (расчёт по формуле раздела 7).

Рассчитывается: новый период, новая дата окончания, стоимость продления, наличие просрочки, штрафные дни, сумма штрафа, общая сумма.

После подтверждения: сохранить старую дату окончания, дату фактического продления, новую дату окончания, стоимость продления, штрафные дни и сумму, добавить запись в архивную таблицу `renewals` (раздел 12), обновить текущую дату окончания в `contracts`, сформировать дополнительное соглашение из шаблона, выгрузить в «Загрузки».

История продлений скрыта по умолчанию, раскрывается по кнопке.

### Расчёт просрочки

Просрочка определяется автоматически по текущей дате и дате окончания аренды. Штрафной тариф определяется выбранным административным режимом из раздела 6.

**Продление после окончания срока:**
```
штрафные_дни = дата_продления − дата_окончания_аренды − 1 день
```
Минимум 0. День оформления нового периода не считается штрафным.
Пример: окончание 27.06.2026, продление 29.06.2026 → штрафных дней: 1.

**Закрытие после окончания срока:**
```
штрафные_дни = дата_закрытия − дата_окончания_аренды
```
Минимум 0.
Пример: окончание 27.06.2026, закрытие 29.06.2026 → штрафных дней: 2.

Сумма штрафа:
```
сумма_штрафа = штрафные_дни × выбранная_штрафная_ставка(высота_ячейки)
```

### Закрытие договора

Функция «Закрыть договор» для занятой ячейки. Сравнивается дата закрытия с датой окончания аренды.

**Досрочное закрытие** (дата закрытия раньше даты окончания): окно «Досрочное расторжение договора», показать текущую дату окончания и количество неиспользованных дней, указать возврат залога (`config.deposit_amount`), указать необходимость закрыть счёт в АБС (заявление формирует АБС, не приложение), запросить подтверждение, сформировать распоряжение о закрытии.

**Обычное закрытие** (дата закрытия = дата окончания): штраф отсутствует, напомнить закрыть счёт в АБС, сформировать распоряжение.

**Закрытие после просрочки** (дата закрытия позже даты окончания): рассчитать штрафные дни и сумму, показать детализацию, после подтверждения сформировать распоряжение.

После окончательного подтверждения закрытия:
1. Сформировать распоряжение о закрытии, выгрузить в «Загрузки».
2. Перенести договор из рабочей таблицы `contracts` в архивную `contracts_archive` с датой и причиной закрытия (раздел 12).
3. Очистить текущую привязку клиента к ячейке.
4. Статус ячейки → «Свободна».

## 12. Две базы данных — рабочая и архивная

Чтобы рабочая база оставалась лёгкой и не перегружалась историческими данными, используются два отдельных файла SQLite:

**Рабочая база (`vault_cells.sqlite3`)** — только то, что нужно для повседневной работы прямо сейчас:
```
vault_defaults  — width_mm, depth_mm (одна строка)
cells           — number, height_mm, width_mm (nullable), depth_mm (nullable)
tariffs         — height_mm, period_from_days, period_to_days, price_per_day
config          — key, value (expiring_soon_days, deposit_amount)
contracts       — только активные договоры аренды (ссылка на cells, данные клиента, даты, стоимость, номер договора, номер счёта)
```

**Архивная база (`vault_archive.sqlite3`)** — история, не нужная для повседневной работы, но обязательная для хранения:
```
contracts_archive — закрытые договоры (полная копия данных договора + дата и причина закрытия)
renewals          — история всех продлений (ссылка на номер договора, даты, стоимость, штраф)
log               — журнал действий (дата, время, сотрудник, ячейка, действие, детали)
```

При закрытии договора он переносится из `contracts` (рабочая база) в `contracts_archive` (архивная база) — не остаётся в обеих сразу.

Обе базы используют одинаковые механизмы надёжности (раздел 2): atomic write, короткие подключения, бэкапы, проверка целостности при старте.

## 13. Персональные данные клиента и защита от перегрузки интерфейса

Хранимые поля: ФИО клиента, серия и номер ID-карты, орган выдачи, дата выдачи документа (если нужна в шаблоне), дата окончания срока действия ID-карты, номер счёта из АБС, номер договора, дополнительные реквизиты по шаблонам.

**Важно:** в подробной карточке ячейки эти персональные данные по умолчанию **полностью скрыты как отдельный блок**, а не показаны частично или в замаскированном виде (никаких «AN\*\*\*\*\*\*45»). Цель — не перегружать интерфейс большим количеством второстепенных заполненных полей. Блок с персональными данными разворачивается целиком только по нажатию кнопки «Показать данные» — до этого момента в карточке видны только оперативно важные поля (номер ячейки, высота, статус, даты аренды, стоимость, штраф — см. раздел 14).

## 14. Подробная карточка занятой ячейки

По умолчанию видно: номер ячейки, высота, текущий статус, дата начала аренды, дата окончания аренды, количество дней до окончания/просрочки, стоимость аренды, залог, количество штрафных дней и сумма штрафа (если есть).

Скрыто за кнопкой «Показать данные» (раздел 13): ФИО клиента, ID-карта, орган выдачи, номер счёта, номер договора, дата оформления первоначального договора, история продлений (дата продления, предыдущая дата окончания, новая дата окончания, срок продления, стоимость продления).

Действия: «Продлить», «Закрыть договор», «Редактировать данные», «Повторно сформировать документ», «Показать данные».

## 15. Редактирование данных

Функция «Редактировать данные» — исправление ошибок сотрудника (ФИО, ID-карта, орган выдачи, номер счёта, номер договора, дата).

При редактировании: сохранять дату изменения и сотрудника (автоматически, по логину Windows — раздел 3) в журнале `log`, не удалять историю аренды/продлений, пересчитывать статус при изменении дат.

Критические поля, влияющие на стоимость/срок, изменяются только после дополнительного подтверждения.

## 16. Требования к интерфейсу

Главный экран: поиск по номеру ячейки, ФИО, номеру счёта; фильтр по высоте, по состоянию; сетка ячеек; счётчики свободно/занято/истекает/просрочено; имя текущего сотрудника (логин Windows) в углу экрана.

Просроченные и истекающие — визуально хорошо заметны.

**Визуальный референс:** приложен HTML-прототип (`seyfy-prototip.html`) — использовать как эталон дизайна (цвета, шрифты, компоновка, стиль карточки/модального окна).

## 17. Проверки и ограничения

Не должно быть возможности: занять уже занятую ячейку; продлить/закрыть свободную ячейку; создать аренду без обязательных данных; дата окончания раньше даты начала; отрицательное количество дней; сохранить продление без новой даты окончания; удалить историю продлений или закрытых договоров; две активные аренды на одну ячейку одновременно.

Перед формированием документов — проверка наличия всех полей шаблона, понятное сообщение при отсутствии.

## 18. Планируемое расширение (не в этой версии)

В будущем — административный раздел с возможностью добавлять новые ячейки (с указанием размеров) или редактировать номера/размеры существующих. Доступ только у администратора (пароль раздела настроек, раздел 3). В текущей версии не реализовывать, только не мешать архитектурой будущему добавлению (например, не хардкодить количество 126 там, где это может измениться).

## 19. Итоговый рабочий процесс

1. Сотрудник выбирает свободную ячейку.
2. Открывается калькулятор, GUI сразу показывает количество дней при вводе дат.
3. Backend считает стоимость по тарифу и переданному количеству дней.
4. Сотрудник озвучивает условия клиенту.
5. При согласии — оформляет клиента и счёт в АБС.
6. Возвращается в приложение, нажимает «Занять», вводит данные клиента/счёта/договора.
7. Приложение сохраняет договор в рабочей базе, формирует документы, выгружает в «Загрузки».
8. Ячейка становится занятой.
9. Далее — продление, закрытие или редактирование.
10. Статусы «Нормально»/«Истекает»/«Просрочено» — автоматически.
11. После закрытия договор переносится в архивную базу, ячейка снова свободна.
