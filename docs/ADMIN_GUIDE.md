# Руководство администратора

## Статус документа

Административные настройки, контролируемое восстановление и переносимая сборка этапа 12 реализованы. Подробная установка и обязательная сетевая приёмка описаны в `docs/DEPLOYMENT_GUIDE.md`.

## Безопасные принципы развёртывания

- На каждом компьютере в папке установки находится собственный скрытый `safe-cells.exe` и локальный конфигурационный файл.
- На рабочем столе создаётся веб-ярлык «Сейфовые ячейки»; сотрудник использует только его.
- В конфиге указывается общая папка; реальный UNC-путь и пароли не коммитятся.
- В общей папке находятся `vault_cells.sqlite3`, `vault_archive.sqlite3`, `templates` и `backups`.
- Обе БД обязаны находиться на одном сетевом томе.
- Обычный запуск не создаёт отсутствующую базу. Первичная инициализация — отдельное подтверждённое действие.
- Общий список сотрудников хранится в рабочей БД. Выбранное при запуске имя хранится только в памяти локального процесса и не связывается с Windows-учёткой.
- WAL запрещён; файловый атрибут Windows «Только чтение» не меняется.

## Переносимое развёртывание

- Сборка создаётся командой `scripts\build_portable.ps1` и проверяется `scripts\smoke_test_portable.py`.
- На рабочий компьютер копируется готовая локальная папка `safe-cells-portable`; установка Python не нужна.
- Рядом с `safe-cells.exe` создаётся локальный `config.json` из примера. Реальный UNC-путь не передаётся в Git.
- `create-shortcut.cmd` один раз создаёт на рабочем столе ярлык «Сейфовые ячейки».
- EXE выбирает свободный порт только на `127.0.0.1`. Входящие подключения с сети не принимаются.
- Обновление страницы не завершает процесс. Закрытие последней вкладки и кнопка «Выйти» завершают только текущий локальный экземпляр.
- Инициализация и миграции не включены в обычный запуск EXE и по-прежнему выполняются отдельно с административного компьютера.

## Первичная настройка

1. Создать отдельную тестовую общую папку без реальных данных.
2. Проверить права чтения/записи и блокировки SMB с компьютеров сотрудников.
3. Выполнить явную инициализацию двух баз один раз.
4. Открыть приложение, нажать шестерёнку настроек и создать один общий пароль отдела не короче 12 символов с буквами и цифрами. После входа на вкладке «Доступ» при необходимости выбрать вариант без пароля.
5. На вкладке «Сотрудники» добавить хотя бы одного активного сотрудника и выбрать его для текущего запуска.
6. До явной инициализации создать в общей папке каталог `templates` и скопировать в него пять утверждённых DOCX-шаблонов с точными именами из раздела ниже.
7. Запустить проверку с 1–3 экземплярами на тестовых данных.
8. Убедиться, что запуск с рабочего стола открывает браузер без окна консоли и без ручного поиска `.exe`.

## Административный раздел

1. На главном экране нажмите маленькую шестерёнку в правом верхнем углу.
2. В зависимости от выбранного режима введите общий пароль либо отметьте предупреждение руководителя. Блокировки попыток и автоматического выхода по времени нет.
3. Используйте верхние вкладки «Общие», «Тарифы», «Шаблоны», «Сотрудники», «Резервные копии» и «Доступ».
4. Измените только нужные значения и нажмите кнопку сохранения на текущей вкладке один раз.
5. На вкладке «Тарифы» выберите один режим штрафа: «Тариф 1–30 дней» либо «Ручная ставка». Во втором режиме обязательно заполните отдельное значение для каждой высоты; эти значения не меняют обычные тарифы аренды.
6. В «Шаблонах» видно назначение, имя файла, наличие файла и найденные поля. Кнопка «Получить копию» выдаёт исходный DOCX.
7. При загрузке поля необязательны: DOCX без полей сохраняется как готовый документ без заполнения. Неизвестные поля по-прежнему запрещены.
8. На вкладке «Сотрудники» добавляйте полные имена и отключайте ушедших сотрудников. Записи не удаляются; последнего активного сотрудника отключить нельзя.
9. После работы нажмите «Закрыть доступ» или закройте окно настроек.

Общий пароль не восстанавливается из хеша. Даже если выбран вход без пароля, сохранённый хеш остаётся для возможного возврата к парольному режиму. Самовольное удаление строки `admin_credentials` запрещено. Пароль, его хеш и индивидуальный путь не следует записывать в документацию или технические логи.

## Бэкапы

После каждой подтверждённой записи приложение создаёт через SQLite Backup API один комплект из двух баз. Сначала скрытый временный каталог получает обе копии и `manifest.json`. Для каждой копии выполняется `quick_check`, записываются имя, размер и SHA-256. Только полностью проверенный каталог публикуется одним переименованием.

В общей папке `backups` сохраняются последние 30 завершённых проверенных комплектов. Временный или неполный каталог комплектом не считается. Обычное копирование активных файлов и замена активной базы после каждой записи запрещены. Ошибка бэкапа после сохранённой бизнес-операции показывается отдельным критическим предупреждением; саму операцию автоматически повторять нельзя.

На вкладке «Резервные копии» видно:

- результат проверки рабочей и архивной баз;
- количество проверенных комплектов;
- количество других активных экземпляров;
- дату, размеры и результат проверки каждого комплекта.

Кнопка восстановления отключена, пока обе активные базы исправны.

## Восстановление

Восстановление никогда не запускается автоматически. После обнаружения повреждения приложение создаёт постоянную блокировку обычных записей и показывает это на вкладке «Резервные копии».

Порядок действий администратора:

1. Убедитесь, что сотрудники прекратили работу, и закройте приложение на остальных компьютерах.
2. На текущем компьютере откройте настройки и вкладку «Резервные копии».
3. Нажмите «Проверить сейчас». Должно быть явно указано, какая база повреждена и что запись заблокирована.
4. Выберите только строку со статусом «Проверен: quick_check и SHA-256 совпадают» и нажмите «Восстановить комплект».
5. Прочитайте предупреждение и подтвердите восстановление. Backend повторно проверит комплект и отсутствие других экземпляров.
6. Дождитесь сообщения об успехе. Обе прежние базы будут сохранены в `damaged-originals/<идентификатор>/`, затем обе активные базы будут восстановлены вместе.
7. Убедитесь, что рабочая и архивная базы снова имеют состояние `ok`. После восстановления автоматически создаётся новый контрольный комплект и обезличенная запись аудита.

Если другой экземпляр найден, проверка экземпляров недоступна, комплект повреждён или сеть пропала, восстановление не выполняется. Не удаляйте каталог `damaged-originals` до анализа администратором. Реальную процедуру до допуска в банк обязательно проверить на тестовом сетевом томе с вымышленными данными.

## Установка DOCX-шаблонов

В общей папке рядом с обеими базами создайте каталог `templates` и поместите в него:

- `Акт приема передач сейф.docx`;
- `Договор индивидуального сейфа ф.л.docx`;
- `Распоряжение Открытие сейф.docx`;
- `Доп. соглашение сейф ф.л.docx`;
- `Распоряжение Закрытие сейф.docx`.

Явная команда `init-db` регистрирует только те файлы из этого списка, которые уже существуют. В дальнейшем администратор может добавить или заменить DOCX через «Настройки». При формировании приложение всегда создаёт новую копию и не изменяет исходник. Файл проверяется до регистрации; после замены всё равно нужна визуальная проверка в Microsoft Word на вымышленных данных.

## Нерешённые входные данные

- фактический UNC-путь.

## Технические команды запуска из исходников

Команды предназначены для разработчика или администратора тестового стенда, не для обычного сотрудника.

Явное создание тестовой пары баз:

```powershell
.\.venv\Scripts\python.exe -m app.cli init-db --config config.local.json --confirm INITIALIZE
```

Обычный запуск никогда не выполняет эту команду автоматически. Перед инициализацией папка уже должна существовать, а путь должен быть указан в локальном конфиге.

Явное обновление существующей тестовой пары со схемы 2 до схемы 3:

```powershell
.\.venv\Scripts\python.exe -m app.cli migrate-v3 --config config.local.json --confirm MIGRATE-TO-3
```

Явное обновление существующей пары со схемы 3 до схемы 4 для состояний «Ключ утерян» и «Занята банком»:

```powershell
.\.venv\Scripts\python.exe -m app.cli migrate-v4 --config config.local.json --confirm MIGRATE-TO-4
```

Явное обновление существующей пары со схемы 4 до схемы 5 для произвольной пометки занятия без договора:

```powershell
.\.venv\Scripts\python.exe -m app.cli migrate-v5 --config config.local.json --confirm MIGRATE-TO-5
```

Каждая команда миграции сначала создаёт согласованный комплект резервных копий обеих баз. Обычный запуск миграцию не выполняет. Обновление 2→5 выполняется последовательно: сначала `migrate-v3`, затем `migrate-v4`, затем `migrate-v5`. Перед производственным обновлением все экземпляры приложения должны быть закрыты.
