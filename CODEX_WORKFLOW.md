# Как вести проект приложения сейфовых ячеек в Codex

## 1. Подготовьте папку проекта

Рекомендуемое расположение:

```text
safe-cells-app/
  AGENTS.md
  START_HERE.md
  PROMPT_01_ARCHITECTURE.md
  PROMPT_02_MILESTONE_1.md
  PROMPT_STAGE_TEMPLATE.md
  REVIEW_PROMPT.md
  data/
    cell_heights.csv
  docs/
    tz-seyfy-novy-proekt.md
    APPROVED_ARCHITECTURE.md
  reference/
    seyfy-prototip.html
```

Открывайте в Codex всю папку `safe-cells-app`, а не отдельный файл.

## 2. Создайте точку возврата

Перед работой желательно создать Git-репозиторий и первый commit исходных файлов. Это позволяет вернуть проект в рабочее состояние, если большая правка окажется неудачной.

Можно дать Codex отдельную команду:

```text
Инициализируй Git-репозиторий в этой папке. Добавь только исходное ТЗ, AGENTS.md, CSV, HTML-референс и служебные Markdown-файлы. Создай первый commit с сообщением "Initial project requirements". Не начинай писать приложение.
```

## 3. Первый запрос — только план

В приложении Codex выберите режим планирования, если он доступен. Если отдельного режима нет, просто отправьте `PROMPT_01_ARCHITECTURE.md`: в нём прямо запрещено писать код.

Codex должен сначала создать документы архитектуры, модели данных, этапов и приёмочных тестов.

Не разрешайте ему сразу переходить к реализации.

## 4. Проверьте архитектурный ответ

Убедитесь, что Codex не отменил утверждённые решения:

- у каждого сотрудника свой `.exe`;
- базы находятся на сетевом диске;
- просмотр использует короткое read-only соединение;
- запись выполняется только после нажатия подтверждающей кнопки;
- используется `BEGIN IMMEDIATE`;
- WAL запрещён;
- есть уникальная защита активной ячейки;
- сетевой сбой не создаёт локальную пустую базу;
- закрытие переносит договор между двумя базами одной транзакцией через `ATTACH DATABASE`.

Если всё верно, попросите Codex записать решения в `docs/DECISIONS.md` и сделать commit документации.

## 5. Первый этап кода

Отправьте текст из `PROMPT_02_MILESTONE_1.md`.

На этом этапе Codex должен сделать только каркас, базы, seed-данные и экран чтения. Не позволяйте ему сразу реализовывать всю аренду.

## 6. Следующие этапы

Для каждого следующего этапа используйте `PROMPT_STAGE_TEMPLATE.md`. Меняйте номер и название этапа согласно `docs/IMPLEMENTATION_PLAN.md`.

Основной принцип: один запрос — один законченный и проверяемый этап.

## 7. После каждого этапа

1. Прочитайте отчёт Codex.
2. Убедитесь, что тесты действительно запускались и есть результат команды.
3. Запустите приложение вручную по его инструкции.
4. Проверьте только функции текущего этапа.
5. Сообщите конкретные ошибки.
6. После исправлений запустите review с текстом из `REVIEW_PROMPT.md`.
7. После успешной проверки создайте Git commit.

## 8. Как сообщать об ошибке

Плохой вариант:

```text
Не работает, исправь.
```

Хороший вариант:

```text
При нажатии кнопки «Обновить» появляется ошибка. До нажатия главная страница открывается. Текст ошибки: [вставить текст]. Исправь только эту проблему, затем запусти связанные тесты и объясни ручную проверку.
```

Также полезно приложить скриншот.

## 9. Чего не писать Codex

Не используйте команды:

- «Сделай всё приложение полностью»;
- «Сам реши все вопросы»;
- «Не проверяй тестами»;
- «Переделай всё как считаешь нужным»;
- «Переходи к следующим этапам без моего подтверждения».

Такие команды создают слишком большой объём изменений, который трудно проверить.
