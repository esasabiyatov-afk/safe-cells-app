# AGENTS.md — приложение учёта банковских сейфовых ячеек

## 1. Роль и способ общения

- Пользователь — владелец требований, не программист.
- Все объяснения, планы, отчёты об ошибках и инструкции по проверке писать на русском языке простыми словами.
- Названия файлов, функций, классов, переменных и таблиц БД — на английском языке.
- Не скрывать ошибки и не утверждать, что проверка пройдена, если команда не запускалась или завершилась ошибкой.
- Не начинать следующий этап реализации без отдельного запроса пользователя.

## 2. Источники требований

Перед любой работой обязательно прочитать:

1. `docs/tz-seyfy-novy-proekt.md` — основной источник функциональных требований.
2. `docs/APPROVED_ARCHITECTURE.md` — утверждённые поправки по архитектуре; они имеют приоритет над противоречащими пунктами исходного ТЗ.
3. `reference/seyfy-prototip.html` — визуальный референс, а не источник бизнес-логики.
4. `data/cell_heights.csv` — реальные seed-данные ячеек.
5. `docs/DECISIONS.md` — утверждённые решения, появившиеся в ходе проекта.
6. `docs/OPEN_QUESTIONS.md` — действительно нерешённые вопросы.

При противоречии применять приоритет:

`APPROVED_ARCHITECTURE.md` → `DECISIONS.md` → основное ТЗ → визуальный прототип.

Не менять утверждённую архитектуру на центральный сервер без прямого запроса пользователя.

## 3. Утверждённая архитектура запуска

- Backend: Python 3.12+, Flask.
- Frontend: обычные HTML, CSS и JavaScript без Node.js, сборщиков и frontend-фреймворков.
- У каждого сотрудника собственный экземпляр `safe-cells.exe` на его Windows-компьютере.
- Каждый экземпляр запускает локальный Flask-сервер на свободном порту и открывает интерфейс в браузере этого же компьютера.
- Рабочая база `vault_cells.sqlite3` и архивная база `vault_archive.sqlite3` лежат в одной общей папке на сетевом диске банка.
- Обычно работает один сотрудник; редко одновременно работают до трёх сотрудников.
- Путь к сетевой папке задаётся в конфигурационном файле и не хардкодится.
- При недоступности сетевого пути запрещено автоматически создавать локальную пустую базу или продолжать работу с устаревшей копией.
- Интернет, CDN, внешние API, телеметрия и облачные ресурсы не используются.
- Закрытие вкладки может завершать только локальный экземпляр приложения этого сотрудника и не должно влиять на приложения других сотрудников.

## 4. Правила доступа к SQLite на сетевом диске

### 4.1. Общий принцип

Соединения с SQLite не держать открытыми постоянно.

Словосочетание «режим только для чтения» означает режим конкретного SQLite-соединения, а не изменение атрибута файла Windows. Не ставить и не снимать атрибут «Только чтение» у файлов БД.

### 4.2. Операции чтения

Для просмотра, поиска, фильтров и открытия карточки:

1. Открыть соединение через SQLite URI с `mode=ro`.
2. Установить `PRAGMA foreign_keys = ON` и разумный `busy_timeout`.
3. Выполнить только `SELECT`.
4. Получить данные.
5. Немедленно закрыть соединение.

Главный экран обновлять при запуске, после сохранения, по кнопке «Обновить» и автоматически примерно раз в 15 секунд. Поиск и фильтры по уже загруженным данным выполнять на frontend.

### 4.3. Операции записи

Соединение чтения/записи открывать только после явного подтверждения действия, которое меняет данные:

- занятие ячейки;
- продление;
- закрытие договора;
- редактирование данных;
- изменение тарифов, настроек или шаблонов.

Каждая операция записи обязана:

1. Открыть короткое read/write-соединение.
2. Установить:
   - `PRAGMA foreign_keys = ON`;
   - `PRAGMA busy_timeout = 15000`;
   - `PRAGMA journal_mode = DELETE`;
   - `PRAGMA synchronous = FULL`;
   - `PRAGMA locking_mode = NORMAL`.
3. Начать транзакцию через `BEGIN IMMEDIATE`.
4. Повторно прочитать актуальное состояние изменяемых данных внутри транзакции.
5. Проверить бизнес-инварианты.
6. Выполнить необходимые `INSERT`, `UPDATE` и/или `DELETE`.
7. Завершить через `COMMIT`.
8. При любой ошибке выполнить `ROLLBACK`.
9. Закрыть соединение в `finally`.
10. После успеха снова прочитать актуальные данные и обновить интерфейс.
11. После успеха создать резервную копию утверждённым способом.

### 4.4. Одновременная работа

- SQLite допускает несколько коротких чтений и только одну операцию записи одновременно.
- Не использовать WAL для базы на сетевом диске.
- Если другая запись не завершилась за время `busy_timeout`, показать понятное сообщение и ничего не менять.
- Нельзя доверять состоянию, ранее показанному в браузере: перед записью обязательно повторить проверку в транзакции.
- На `contracts.cell_number` должно быть уникальное ограничение или уникальный индекс, запрещающий две активные аренды одной ячейки.
- Ограничения БД являются последней линией защиты, даже если проверка уже выполнена в Python.

### 4.5. Две базы

- Обе базы размещать в одной сетевой папке и на одном сетевом томе.
- Операции, одновременно меняющие рабочую и архивную базы, выполнять через `ATTACH DATABASE` в одной транзакции при `journal_mode=DELETE`.
- Для закрытия договора сначала вставить полную архивную запись и журнал, затем удалить активный договор — всё в рамках одной транзакции.
- Добавить тесты на частичный сбой и повтор операции.

### 4.6. Ошибки сети

- При ошибке чтения показать: «Не удалось получить данные с сетевого диска. Проверьте подключение к сети».
- При неопределённом результате записи не повторять операцию автоматически.
- После восстановления связи сначала заново прочитать базу и определить, была ли операция фактически сохранена.
- Не скрывать сетевые ошибки и не подменять общую базу локальной.

## 5. Резервное копирование и восстановление

- Не заменять активный файл SQLite временным файлом после каждой записи.
- Не копировать активный файл БД обычным `shutil.copy` во время возможной записи.
- После успешной транзакции создавать согласованный бэкап через SQLite Backup API.
- Сначала создавать бэкап под временным именем, проверять его, затем переименовывать в окончательное имя.
- Хранить последние 30 комплектов резервных копий рабочей и архивной базы.
- Восстановление не выполнять автоматически, пока другие экземпляры приложения могут работать.
- При повреждении заблокировать операции записи, показать понятную ошибку и предложить администратору режим восстановления.
- Перед восстановлением убедиться, что другие экземпляры приложения закрыты, и сохранить повреждённые файлы отдельно для анализа.

## 6. Защита данных

- Не добавлять реальные персональные данные в тесты, фикстуры, скриншоты и документацию.
- Не писать полные данные клиента, ID-карту и номер счёта в технические логи.
- Использовать параметризованные SQL-запросы; не собирать SQL строковой конкатенацией.
- Экранировать пользовательские данные в HTML.
- Административный пароль не хранить открытым текстом; хранить стойкий хеш с солью.
- Секреты, пароли и индивидуальные сетевые пути не коммитить в репозиторий.

## 7. Бизнес-правила, которые нельзя менять

- Начальная и конечная даты аренды включаются в срок: `days = end_date - start_date + 1`.
- При вводе дней: `end_date = start_date + days - 1`.
- Тариф выбирается по общей длительности аренды целиком, без ступенчатого разбиения.
- Штрафная ставка всегда равна тарифу диапазона до 30 дней для высоты ячейки.
- Продление после окончания: `penalty_days = max(0, renewal_date - old_end_date - 1 day)`.
- Закрытие после окончания: `penalty_days = max(0, close_date - end_date)`.
- Нельзя иметь две активные аренды одной ячейки.
- Нельзя занять занятую ячейку, продлить или закрыть свободную.
- Закрытые договоры и история продлений не удаляются из архива.
- Персональные данные в карточке по умолчанию полностью скрыты до нажатия «Показать данные».
- Высота — точный размер, а не категория «малая/средняя/большая».
- Количество ячеек не хардкодить как 126 в бизнес-логике.

## 9. Порядок реализации

Работать этапами:

1. Архитектура, схема данных, риски и план.
2. Каркас Flask, конфигурация сетевого пути, инициализация двух БД и seed-данные.
3. Read-only чтение ячеек, статусы, поиск, фильтры и главный экран.
4. Калькулятор аренды и тесты границ тарифов.
5. Создание активного договора с короткой транзакцией и защитой от гонки.
6. Карточка занятой ячейки и скрываемые персональные данные.
7. Продление и штрафы.
8. Закрытие и атомарный перенос в архив через `ATTACH DATABASE`.
9. Шаблоны DOCX и выгрузка документов.
10. Настройки администратора.
11. Бэкапы, проверки целостности и контролируемое восстановление.
12. PyInstaller, инструкция развёртывания и приёмочные тесты на 1–3 компьютерах.

## 10. Протокол выполнения каждой задачи

Перед редактированием:

1. Прочитать относящиеся к задаче файлы.
2. Кратко описать понимание задачи.
3. Назвать затрагиваемые файлы.
4. Указать риски и проверки.

Во время реализации:

- Делать минимальное законченное изменение.
- Не менять несвязанные части проекта.
- Не добавлять производственные зависимости без объяснения необходимости.
- Сохранять совместимость с Windows и UNC-путями.
- Для тестов использовать временные локальные базы, не сетевую производственную папку.

После реализации:

1. Запустить релевантные тесты.
2. Запустить полный набор тестов, если это разумно.
3. Для UI дать точные шаги ручной проверки.
4. Показать список изменённых файлов.
5. Сообщить, что сделано, что не сделано и какие риски остались.
6. Не начинать следующий этап автоматически.

## 11. Обязательное тестирование

Использовать `pytest`. Обязательные тесты:

- включительное вычисление дней и границы 1, 30, 31, 90, 91, 180, 181 дней;
- тариф для каждой высоты и диапазона;
- обе формулы штрафных дней;
- статусы normal/expiring/overdue на граничных датах;
- запрет второй активной аренды одной ячейки;
- повторная проверка ячейки внутри write-транзакции;
- обработка `database is locked` без частичного сохранения;
- невозможные переходы состояния;
- импорт 126 уникальных строк из CSV;
- перенос договора в архив через две подключённые базы;
- откат после имитированного частичного сбоя;
- ошибка при недоступном сетевом пути без создания локальной БД;
- проверка обязательных полей шаблона;
- отсутствие реальных персональных данных в логах.

Тесты дат должны использовать фиксированную переданную дату, а не напрямую `datetime.now()`.

## 12. Критерий готовности изменения

Задача считается выполненной только когда:

- поведение соответствует ТЗ, `APPROVED_ARCHITECTURE.md` и `DECISIONS.md`;
- проверки входных данных реализованы на backend, а frontend-проверки используются только для удобства;
- тесты добавлены и успешно выполнены;
- нет необъяснённых изменений вне задачи;
- документация обновлена, если изменился запуск или поведение;
- Codex дал понятные шаги ручной проверки;
- пользователь явно принял этап либо сообщил ошибки.
